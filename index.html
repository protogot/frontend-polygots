    01

    Rendering Strategies Deep DiveCSR vs SSR vs SSG vs ISR, plus Streaming and Server Components

    Core Web VitalsHydrationNext.jsCDN caching
    60-second answer

    A rendering strategy decides where HTML is produced (browser, server, build machine, edge) and when (per request, at build, or on revalidation). That choice trades TTFB, LCP, interactivity, freshness, SEO and infrastructure cost against each other. I don't pick one per app. I pick one per route: SSG/ISR for public, cacheable content; streaming SSR for personalised or SEO-critical dynamic pages; CSR for authenticated, highly interactive surfaces behind login. Then I minimise hydration cost with Server Components and code splitting.

    Core definitions

    CSR · Client-Side

    The server returns an almost empty HTML shell plus JS. The browser downloads and executes the bundle, fetches data, then builds the DOM.

    SSR · Server-Side

    Per request, the server runs components, resolves data and returns full HTML. The client then downloads JS and hydrates it.

    SSG · Static Generation

    HTML is produced once at build time and served as static files from a CDN. Every user gets identical bytes.

    ISR · Incremental Static

    SSG pages are regenerated in the background after a revalidation window or an explicit purge, without a full rebuild.

    1. Client-Side Rendering (CSR)

    1
    Browser requests /dashboard; server returns <div id="root"></div> plus <script src="main.js">.
    2
    The browser downloads, parses and compiles the bundle. The main thread is busy and the screen is blank.
    3
    The app mounts, shows spinners, and fires API requests (the second network round trip).
    4
    Data arrives, React renders, and the LCP element finally paints.

    Why LCP suffers: it is a serial waterfall (HTML → JS → data → render). On a mid-range Android phone over 4G, a 300 KB gzipped bundle can cost 1–3 s of parse and execute time alone.

    Where it wins: no per-request server compute, trivially cacheable shell, simple deployment (S3 + CDN), and excellent for long-lived sessions where navigation after the first load is instant.

    Mitigations: route-level code splitting, <link rel="preload"> for critical data and fonts, kicking off data fetches in parallel with the bundle (render-as-you-fetch), skeleton UIs to avoid CLS, and a service worker for repeat visits.

    2. Server-Side Rendering (SSR)

    1
    Request hits the server or edge function. It authenticates, fetches data (DB/APIs), and renders the component tree to HTML.
    2
    HTML is sent, either all at once (renderToString) or streamed in chunks (renderToPipeableStream / renderToReadableStream).
    3
    The browser paints meaningful content immediately (fast FCP/LCP), while the JS bundle downloads.
    4
    Hydration: React re-runs the components on the client, builds the fiber tree, matches it against the existing DOM, and attaches event handlers.
    The "uncanny valley" of hydration

    The page looks ready but is not interactive until hydration finishes. Clicks during that window are lost or delayed, which shows up as poor INP and rage clicks. Hydration cost scales with the amount of JS and component tree size, not the HTML size.

    Bottlenecks: TTFB is bound by the slowest upstream call (without streaming), server CPU scales with traffic, and the full HTML plus a JSON data payload are both shipped (the "double data" problem).

    Caching SSR: responses that are not personalised can still be cached at the CDN with Cache-Control: public, s-maxage=60, stale-while-revalidate=300, which effectively gives you ISR-like behaviour at the edge.

    3. Static Site Generation (SSG)

    At build time, the framework enumerates routes (generateStaticParams / getStaticPaths), fetches data, and writes HTML + JSON files that are uploaded to object storage and fronted by a CDN.

    • Performance: TTFB is a CDN cache hit (often <50 ms globally); the origin never sees traffic, so traffic spikes are a non-event.
    • Security: no runtime server means a minimal attack surface.
    • Trade-off: build time is O(N) in the number of pages. 100k product pages × 50 ms = ~83 minutes. Content is stale until the next deploy.
    • Personalisation: done client-side after load (e.g. cart badge, "Hi, Asha"), or at the edge via middleware that rewrites to static variants (A/B buckets, locale).

    4. Incremental Static Regeneration (ISR)

    ISR applies stale-while-revalidate semantics to static pages:

    1
    Request for /products/123: the CDN serves the cached HTML instantly.
    2
    If the page is older than revalidate (e.g. 60 s), the stale page is still served, and one background regeneration is triggered.
    3
    On success, the cache entry is atomically replaced. On failure, the old page keeps serving (graceful degradation).
    4
    Pages not generated at build time can be rendered on first request (dynamicParams / fallback) and then cached.
    // Next.js App Router: time-based + on-demand ISR
export const revalidate = 60; // seconds

export default async function ProductPage({ params }) {
  const product = await fetch(`https://api.shop.com/products/${params.id}`, {
    next: { tags: [`product:${params.id}`] },
  }).then(r => r.json());
  return <Product data={product} />;
}

// app/api/revalidate/route.ts: called by the CMS webhook
import { revalidateTag } from 'next/cache';
export async function POST(req) {
  const { id, secret } = await req.json();
  if (secret !== process.env.REVALIDATE_SECRET) return new Response('Unauthorized', { status: 401 });
  revalidateTag(`product:${id}`);
  return Response.json({ revalidated: true });
}

    Staff-level concerns: cache stampedes when many pages expire at once (stagger revalidation windows), consistency across many CDN PoPs (tag-based purge rather than per-URL), and the visibility of stale prices or stock (keep price and stock client-fetched, or use on-demand invalidation from the inventory service).

    Beyond the big four

    Streaming SSR

    Send the shell immediately and stream Suspense boundaries as data resolves. TTFB is no longer bound by the slowest query.

    React Server Components

    Components that run only on the server and ship zero JS. Only "use client" islands hydrate, so hydration cost drops sharply.

    Islands (Astro)

    Static HTML page with isolated interactive widgets that hydrate independently (client:visible).

    Partial Prerendering

    A static shell is served from the CDN instantly, with dynamic holes streamed in from the server in the same response.

    Interviewer follow-ups

    How does Streaming SSR differ from traditional SSR?

    Traditional SSR (renderToString) is all or nothing: the server waits for every data dependency, then sends one HTML string. A slow recommendations API delays the whole page.

    Streaming SSR (renderToPipeableStream) flushes the shell as soon as it is ready and renders <Suspense fallback> placeholders for pending parts. When each promise resolves, React streams an HTML chunk plus a tiny inline script that swaps the fallback for the real content, all over the same HTTP response.

    It also enables selective hydration: each Suspense boundary hydrates independently, and React prioritises the boundary the user is interacting with. The results are lower TTFB, earlier FCP, and better INP.

    What is a hydration mismatch and how do you fix it?

    Hydration assumes the first client render produces exactly the same markup as the server. Common causes of mismatches:

    • Reading browser-only values during render: window.innerWidth, localStorage, navigator.language.
    • Non-deterministic values: Date.now(), Math.random(), generated IDs.
    • Timezone and locale formatting differences between server and client.
    • Invalid HTML nesting (<div> inside <p>), which the browser parser "fixes" so the DOM no longer matches.
    • Browser extensions injecting nodes.

    Fixes: use useId for IDs; move browser-only logic into useEffect with a two-pass render (const [mounted, setMounted] = useState(false)); pass a server-determined timestamp or timezone as a prop; use suppressHydrationWarning only for unavoidable leaf text like timestamps; or render that component client-only (dynamic(..., { ssr: false })).

    In React 18+, a mismatch causes React to discard the server HTML up to the nearest Suspense boundary and client-render it. That costs performance and can cause layout shift.

    How are Server Components different from SSR?

    SSR is a delivery technique: render components to HTML on the server, then ship all of their JS to hydrate. RSC is a component type: server components never ship their code to the client. They serialise their output into the RSC payload, and only client components hydrate.

    They are complementary. Next.js uses RSC to decide what JS ships and SSR to turn the initial tree into HTML. RSC can also refetch a subtree on navigation without a full page load.

    How would you migrate a large CSR SPA to SSR without a big-bang rewrite?
    • Measure first: identify the routes where LCP and SEO matter (landing, product, search), usually 10–20% of routes and 80% of traffic.
    • Introduce a meta-framework shell and route only those paths to it at the edge or proxy (strangler fig pattern). The rest stays in the SPA.
    • Audit code for SSR safety: window/document access at module scope, singletons that leak state across requests, and libraries without SSR support.
    • Move data fetching to the server layer; keep API contracts identical.
    • Roll out behind a feature flag, compare RUM metrics (LCP, INP, conversion) per cohort, and expand.

    Web Performance & CDN ArchitectureMaking the first load fast and keeping it fast at scale

    Critical Rendering PathResource HintsCache-ControlEdge
    60-second answer

    I think about landing speed in three layers. Network: get bytes closer and fewer (CDN, HTTP/2–3, Brotli, immutable caching). Critical path: unblock the first render (inline critical CSS, defer JS, preload the LCP image and fonts). Main thread: ship less JS (code splitting, tree shaking, Server Components) so the page becomes interactive quickly. For the CDN, I use content-hashed assets with one-year immutable caching, short or revalidated caching for HTML, and tag-based purges for on-demand updates.

    The browser cannot paint until it has the DOM and the CSSOM. CSS is render-blocking; classic synchronous <script> is parser-blocking (and also waits for preceding CSS).

    Over-preloading backfires

    Every preload competes for bandwidth with the LCP resource. Preload only what the browser would discover late, and verify it in the waterfall.

    Shipping less JavaScript

    • Route-based splitting with React.lazy(() => import('./Checkout')), plus component-level splitting for heavy widgets (editors, charts, maps).
    • Tree shaking requires ESM and "sideEffects": false; avoid barrel files that defeat it.
    • Bundle budgets in CI (size-limit, bundlesize) fail PRs that exceed budget; inspect with source-map-explorer.
    • Third-party scripts are often the biggest cost: load after interaction, use facades for embeds (YouTube), or offload to a worker (Partytown).
    • Serve modern bundles without unnecessary polyfills; target an up-to-date browserslist.

    How a CDN works internally

    1
    Routing: anycast IP or GeoDNS sends the user to the nearest point of presence (PoP). TLS terminates there, so the handshake round trips are short.
    2
    Cache key: usually scheme + host + path + (selected) query string + headers named in Vary. A poorly normalised key (tracking params, cookies) destroys the hit ratio.
    3
    Hit: served from edge memory or SSD. Miss: the request goes to a regional tier or origin shield, then the origin. Request coalescing collapses concurrent misses into one origin fetch.
    4
    The response is stored according to Cache-Control / s-maxage / Surrogate-Control, then compressed and served.

    Edge compute (Cloudflare Workers, Lambda@Edge, Akamai EdgeWorkers) adds logic at the PoP: auth checks, A/B bucketing, geo redirects, header rewrites, and even full SSR near the user.

    What to cache and how to invalidate

    Cache busting

    Content-hashed filenames (main.a1b2c3.js). A new deploy produces new URLs, so nothing has to be purged. Deploy assets before the HTML that references them.

    Programmatic purge

    API call by URL, prefix, or surrogate key / cache tag (Cache-Tag: product-123). Tag purges scale to thousands of URLs.

    Revalidation

    Short TTL + stale-while-revalidate, or ETag validation. No coordination needed; bounded staleness.

    Never edge-cache: responses that depend on cookies or auth (unless the key varies on a normalised segment), Set-Cookie responses, and anything with PII.

    Classic production incident

    A personalised page is cached with public, so user A's name and cart are served to user B. Default to private for any authenticated response, and strip Set-Cookie on cacheable routes.

    Interviewer follow-ups

    LCP regressed from 2.1 s to 3.4 s after a release. How do you investigate?
    • Confirm in RUM, not just the lab: which pages, devices, countries, and percentiles? Correlate with the deploy timestamp.
    • Break LCP into its four sub-parts: TTFB, resource load delay, resource load time, and element render delay. That tells you whether it's the server, discovery, bytes, or main thread.
    • Diff bundles between releases (new dependency? lost code split?) and check whether the LCP element changed (a new hero carousel, or a lazy-loaded hero image).
    • Check the CDN hit ratio: did cache keys or headers change (a new query param, Vary: Cookie)?
    • Fix, add a Lighthouse CI budget for that template, and alert on the p75 RUM metric.
    Why is HTTP/2 domain sharding an anti-pattern?

    HTTP/1.1 allowed about 6 connections per origin, so sharding across subdomains increased parallelism. HTTP/2 multiplexes many streams over one connection with header compression and prioritisation. Sharding now adds extra DNS lookups and TLS handshakes and breaks prioritisation. HTTP/3 (QUIC over UDP) additionally removes TCP head-of-line blocking and supports 0-RTT resumption.

    How do you deploy without users getting a broken mix of old HTML and new JS?

    Upload new hashed assets first (they don't collide with old ones), keep old assets for N days for tabs still open, then switch the HTML or manifest. Handle ChunkLoadError for long-lived SPA tabs by reloading on a failed dynamic import, or by version polling and prompting the user to refresh.

    Client Storage, Auth Tokens & SecurityXSS vs CSRF, cookies vs localStorage, CSP

    HttpOnlySameSiteCSPOAuth / BFF
    60-second answer

    Anything readable by JavaScript is readable by an XSS payload, so long-lived credentials must not live in localStorage. My default is a refresh token in an HttpOnly, Secure, SameSite cookie (ideally scoped to a backend-for-frontend), with a short-lived access token in memory or the session handled entirely by the BFF. Cookies solve token theft but reintroduce CSRF, which I close with SameSite, CSRF tokens or custom headers, and Origin checks. XSS itself is prevented with framework auto-escaping, sanitisation, a strict nonce-based CSP, and Trusted Types.

    Recommended token architecture

    1
    User logs in through the OAuth Authorization Code + PKCE flow.
    2
    The server sets the refresh token as __Host-rt; HttpOnly; Secure; SameSite=Strict; Path=/. The access token (5–15 min) is returned in the body and held only in memory.
    3
    API calls send Authorization: Bearer <access>. A custom header also defeats classic CSRF.
    4
    On 401 or page reload, call /refresh (the cookie is sent automatically) and get a new access token. Rotate the refresh token on every use and detect reuse.
    5
    Logout clears the cookie server-side and revokes the refresh token family.
    Even stronger: Backend-for-Frontend (BFF)

    The browser holds only an opaque HttpOnly session cookie. The BFF stores OAuth tokens server-side and proxies API calls. Tokens never touch JavaScript, so even a successful XSS cannot exfiltrate them. It can still act as the user while the page is open, which is why XSS prevention remains essential.

    Cross-Site Scripting (XSS)

    Stored

    Payload persisted in the DB (comment, profile name) and rendered to every viewer.

    Reflected

    Payload in a URL or form is echoed back immediately by the server: ?q=<script>…

    DOM-based

    Entirely client-side: el.innerHTML = location.hash. The server never sees it.

    Defence in depth

    • Context-aware encoding: React escapes text by default. Danger zones are dangerouslySetInnerHTML, href={userUrl} (javascript: URLs), eval, new Function, and innerHTML in refs.
    • Sanitise rich HTML with DOMPurify.sanitize(html) and allow-list URL schemes (https:, mailto:).
    • Strict CSP blocks injected inline scripts even if markup gets through.
    • Trusted Types make dangerous DOM sinks reject plain strings, enforced by the browser.
    • HttpOnly cookies limit the blast radius, and Subresource Integrity covers third-party scripts.
    Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-r4nd0m' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self';
  require-trusted-types-for 'script';
  report-to csp-endpoint

    Roll CSP out with Content-Security-Policy-Report-Only first, collect violations, then enforce.

    Cross-Site Request Forgery (CSRF)

    The attacker's page makes the victim's browser send a request to bank.com. The browser attaches bank cookies automatically, so the server sees an authenticated request. The attacker can't read the response, but the side effect (a transfer) happens.

    <!-- evil.com -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="5000">
</form>
<script>document.forms[0].submit()</script>
    • SameSite=Lax/Strict is the primary defence today. Note that "same-site" means the same registrable domain, so a compromised sibling subdomain is still same-site.
    • Synchronizer token: the server issues a random token in the page or session; state-changing requests must echo it in a header or body field.
    • Double-submit cookie: a token in a readable cookie plus the same value in a header; the server compares them (sign it to prevent injection).
    • Custom headers (Authorization, X-Requested-With) force a CORS preflight, which cross-origin pages can't pass.
    • Verify Origin / Sec-Fetch-Site headers on mutations, and never mutate state on GET.
    Common misconception

    CORS does not prevent CSRF. CORS controls whether a page can read a response. Simple requests (form POSTs) are still sent with cookies.

    Interviewer follow-ups

    If tokens are in memory, how do you survive a page refresh or multiple tabs?

    On boot, call the refresh endpoint (the HttpOnly cookie is sent automatically) to mint a new access token, and show a skeleton until it resolves. For multiple tabs, each tab refreshes independently, or tabs coordinate through BroadcastChannel or the Web Locks API so only one refresh runs at a time (avoiding refresh-token rotation races). Logout is broadcast to every tab the same way.

    Is JWT in localStorage ever acceptable?

    For low-risk apps with short-lived tokens and a strong CSP it is a conscious trade-off, but a single XSS lets an attacker exfiltrate the token and use it from anywhere until it expires. With HttpOnly cookies, an XSS can only act while the victim's tab is open. At staff level, I'd document the threat model and default to the cookie or BFF approach for anything handling money or PII.

    How do you safely render user-supplied Markdown?

    Convert Markdown to HTML with raw HTML disabled, then pass the output through DOMPurify with an allow-list of tags and attributes, force rel="noopener noreferrer" and target="_blank" on links, and reject non-http(s) URLs. Ideally sanitise on both server (at write time) and client (at render time), behind CSP and Trusted Types.

    React State ArchitectureChoosing the right home for each kind of state, and URL-driven filters

    useState / useReducerContextZustand / ReduxReact QueryURLSearchParams
    60-second answer

    The biggest state-management mistake is treating all state the same. I classify it first. Server state is cached remote data, so it belongs in React Query or RTK Query. URL state is anything shareable or bookmarkable, like filters, sorting, pagination and tabs. Local UI state stays in the component. Truly global client state (auth session, theme, feature flags) goes in Context if it changes rarely, or a selector-based store like Zustand or Redux if it changes often. Once server state moves to a query cache, the "global store" usually shrinks by around 80%.

    Local state: useState vs useReducer

    Use useReducer when the next state depends on the previous one in non-trivial ways, or when multiple values change together. It centralises transitions and makes them unit-testable as pure functions. Colocate state as low as possible, and lift it only to the nearest common ancestor.

    type State = { status: 'idle' | 'loading' | 'error'; items: Item[]; error?: string };
type Action =
  | { type: 'fetch' }
  | { type: 'success'; items: Item[] }
  | { type: 'failure'; error: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'fetch':   return { ...state, status: 'loading' };
    case 'success': return { status: 'idle', items: action.items };
    case 'failure': return { ...state, status: 'error', error: action.error };
  }
}

    Context API: dependency injection, not a state manager

    When a provider's value changes by reference, every consumer re-renders, even consumers that only use a field that didn't change. There is no built-in selector.

    • Split contexts by update frequency, for example AuthContext separate from CartContext.
    • Separate state and dispatch into two contexts; components that only dispatch never re-render.
    • Memoise the value: useMemo(() => ({ user, login }), [user]), otherwise a new object every render re-renders every consumer.
    • For high-frequency updates, use a store with useSyncExternalStore and selectors.

    Global stores

    Redux Toolkit

    A single immutable tree, actions and reducers, DevTools time travel, middleware. Best for large teams needing strict conventions and auditability.

    Zustand

    A tiny hook-based store with selector subscriptions and no provider. Minimal boilerplate and very fast.

    Jotai / Recoil

    Atomic, bottom-up state. Components subscribe to individual atoms, and derived atoms form a dependency graph.

    Signals

    Fine-grained reactivity (Preact Signals, Solid, Angular). Updates the exact DOM node without re-rendering components.

    import { create } from 'zustand';

const useCart = create<CartState>()((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
}));

// Re-renders ONLY when the count changes, not on every cart mutation
const count = useCart((s) => s.items.length);

    Server state: the biggest simplification

    Remote data is a cache of something you don't own, so it needs deduplication, background refetching, staleness, retries, pagination, optimistic updates and invalidation. Hand-rolling that in Redux with thunks is where most complexity comes from.

    URL-driven search and filter state

const FilterSchema = z.object({
  q: z.string().default(''),

  const update = useCallback((patch, { replace = false } = {}) => {
    const next = { ...filters, ...patch, page: patch.page ?? 1 }; // reset page on filter change
    const sp = new URLSearchParams();
    Object.keys(next).sort().forEach((k) => {        // canonical order = better cache hits

    });
    setParams(sp, { replace });
  }, [filters, setParams]);

  return [filters, update] as const;
}

    How do you prevent race conditions when filters change quickly?

    Evolutionary Architecture of ReactFrom Fiber to Concurrent React, Server Components and the Compiler

    FiberHooksConcurrent renderingRSCReact Compiler
    60-second answer

    React's evolution is one long arc toward interruptible, prioritised rendering and shipping less JavaScript. React 16 rewrote the core as Fiber, which turns rendering into small units of work that can pause; Hooks arrived in 16.8. React 17 had no new features but made upgrades incremental by attaching events to the root container. React 18 turned on concurrent rendering: automatic batching, transitions, streaming SSR with selective hydration, and useId. React 19 moved work to the server with Server Components and Actions, added use, useOptimistic and useActionState, and the React Compiler removes most manual memoisation.

    React 16: the Fiber rewrite (2017)

    The old "stack reconciler" walked the tree recursively and synchronously. Once a render started, it couldn't stop, so large updates blocked the main thread and dropped frames.

    Fiber reimplements the call stack as a linked list of fiber nodes (child, sibling, return), each representing a unit of work. That makes it possible to:

    • Split rendering into two phases. In the render/reconcile phase, React computes changes; this phase is pure, interruptible, and can be restarted. In the commit phase, React applies DOM mutations and runs layout effects synchronously, and it can't be interrupted.
    • Prioritise updates (later formalised as "lanes"): user input beats data fetches, which beat offscreen work.
    • Double buffering: React keeps a current tree and a workInProgress tree and swaps them on commit.

    Also in the 16.x line: Error Boundaries (componentDidCatch, getDerivedStateFromError), Portals, Fragments, the new Context API (16.3), React.lazy + Suspense for code splitting (16.6), and Hooks (16.8), which allow state and effects in function components and replaced HOCs and render props for logic reuse.

    React 17: the stepping-stone release (2020)

    • Event delegation moved from document to the root container (rootNode.addEventListener). Multiple React versions can now coexist on one page, which enables gradual upgrades and micro-frontends.
    • New JSX transform: no more import React in every file; the compiler imports react/jsx-runtime.
    • Event pooling removed: e.persist() is no longer needed.
    • Effect cleanup became asynchronous (it runs after paint), and onScroll no longer bubbles.

    React 18: concurrent React (2022)

    Concurrency is opt-in through createRoot and is triggered by specific APIs. It's not a mode you switch on globally.

    Automatic batching

    Updates in promises, setTimeout and native handlers are batched into one render (previously only inside React event handlers). Use flushSync to opt out.

    Transitions

    useTransition / startTransition mark updates as non-urgent. They're interruptible, so typing stays responsive while results re-render.

    useDeferredValue

    Renders with the old value first, then re-renders with the new one in the background. Useful when you don't control the setter.

    Streaming SSR

    renderToPipeableStream with Suspense lets HTML stream, and selective hydration prioritises the part the user clicks.

    New hooks

    useId (SSR-stable IDs), useSyncExternalStore (tear-free external stores), useInsertionEffect (CSS-in-JS).

    Interviewer follow-ups

    Why do Hooks have to be called in the same order on every render?

    React stores hook state as a linked list on the fiber (memoizedState). On each render it walks that list by position, so the first useState call reads slot 1, the second reads slot 2, and so on. Calling hooks conditionally shifts the positions and assigns the wrong state to the wrong hook. Hence the Rules of Hooks, enforced by the ESLint plugin. The use hook is the exception because it doesn't store state in a slot.

    Does concurrent rendering make React multi-threaded?

    No. Everything still runs on the main thread. Concurrency means React can pause rendering work, yield to the browser (about every 5 ms via its scheduler, which uses MessageChannel) so input and paint can happen, then resume, restart, or abandon the work if a higher-priority update arrives. Only the render phase is interruptible; the commit phase is always synchronous.

    Will the React Compiler make useMemo obsolete?

    Mostly, for performance memoisation. The compiler memoises values, callbacks and JSX at a finer granularity than humans typically do. You may still need useMemo for semantic guarantees (a stable reference that an external library depends on), or when the compiler bails out on code that breaks the Rules of React (mutating props, reading refs during render). Staff-level work here means enabling the ESLint compiler rule and fixing violations first.

    JavaScript Runtime InternalsEvent loop (browser and Node.js), V8 pipeline, Virtual DOM reconciliation

    Call stackMicrotaskslibuvV8 JITReconciliation
    60-second answer

    JavaScript runs on one main thread with one call stack. Concurrency comes from the host environment (browser Web APIs, or Node.js with libuv), which does I/O and timers elsewhere and queues callbacks. The event loop picks one macrotask, runs it to completion, drains every microtask (promise reactions, queueMicrotask), lets the browser render if it's time, and repeats. That's why a resolved promise always runs before a setTimeout(fn, 0), and why a long synchronous task freezes both input and rendering.

    Node.js architecture: single thread or multi-thread?

    The diagram traces this program:

    console.log("Start");
setTimeout(() => { console.log("Timeout"); }, 0);
console.log("End");
// Output: Start → End → Timeout
    1
    Application → V8: V8 pushes console.log("Start") onto the call stack, executes it, and "Start" goes to Output.
    2
    V8 → Node API: setTimeout isn't part of JavaScript. V8 calls Node's timer binding, which registers a timer with libuv and returns immediately. V8 doesn't wait.
    3
    V8 runs console.log("End"). The script finishes and the call stack is empty.
    4
    libuv: when the timer expires, its callback becomes runnable in the timers phase of the event loop (the "Event Queue" in the diagram).
    5
    Execute callback: the event loop hands the callback back to V8, which runs it on the same main thread, and "Timeout" is printed.

    Where do the "Worker Threads" come in?

    Blocking operations that the OS can't do asynchronously are offloaded to libuv's thread pool (4 threads by default, configurable with UV_THREADPOOL_SIZE): file system calls, dns.lookup, crypto.pbkdf2/scrypt, and zlib. When a pool thread finishes, it posts a completion to the event loop, and the JS callback runs on the main thread.

    Nuance worth saying in an interview

    Most network I/O doesn't use the thread pool. libuv uses the OS's non-blocking readiness APIs (epoll on Linux, kqueue on macOS, IOCP on Windows) directly from the event loop thread. So the honest answer to "Is Node single-threaded?" is: your JavaScript runs on one thread, but Node itself is multi-threaded (thread pool, V8 GC and compiler threads, and optional worker_threads for CPU-bound JS).

    The browser event loop, step by step

    1
    Pick the oldest runnable task (macrotask) from a task queue (script, setTimeout, setInterval, MessageChannel, I/O, user input) and run it to completion.
    2
    Drain the microtask queue completely: promise .then/.catch/.finally, await continuations, queueMicrotask, MutationObserver. Microtasks queued during this step also run now, so an infinite microtask chain starves rendering.
    3
    If it's time to render (about every 16.7 ms at 60 Hz and the page is visible): run requestAnimationFrame callbacks → style → layout → ResizeObserver → paint → composite.
    4
    If there's idle time before the next frame, run requestIdleCallback callbacks. Then loop.

    Keeping the main thread responsive

    A long task is anything over 50 ms. During it, no input is handled and nothing paints, which directly harms INP.

    async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    process(items[i]);

    Yielding with await Promise.resolve() does not help, because microtasks run before rendering. You need a task boundary (setTimeout, MessageChannel, or scheduler.yield()). For CPU-heavy work (parsing, image processing, diffing), move it to a Web Worker.

    The V8 execution pipeline

    1
    Parse: source → tokens → AST. Lazy parsing pre-parses functions and only fully parses them when first called.
    2
    Ignition (interpreter) generates compact bytecode and collects type feedback in inline caches.
    3
    Sparkplug (baseline compiler) quickly turns bytecode into unoptimised machine code. Maglev (mid-tier) does fast optimisation.
    4
    TurboFan (optimising JIT) speculatively compiles hot functions using observed types, for example "this is always a Point with x and y".
    5
    Deoptimisation: if an assumption breaks (a different object shape arrives), V8 bails out to bytecode and may re-optimise later.
    • Hidden classes (shapes): objects created with the same properties in the same order share a shape, so property access becomes a fixed offset. Adding properties in different orders or using delete creates new shapes and polymorphism.
    • Inline caches: monomorphic call sites (one shape) are fastest; megamorphic sites (more than 4 shapes) fall back to slow lookups.
    • Garbage collection (Orinoco): generational. A young-generation scavenger handles short-lived objects, and the old generation uses concurrent and incremental mark-compact to keep pauses short.

    Virtual DOM and reconciliation

    The "Virtual DOM" is a tree of plain JS objects (React elements) describing the UI. On a state update, React re-renders the affected components into a new element tree, diffs it against the previous fiber tree, and commits the minimal set of real DOM mutations in one batch.

    A general tree diff is O(n³). React's heuristic diff is O(n), based on two assumptions:

    • Different element types produce different trees. <div> → <span>, or <A/> → <B/>, tears down the whole subtree (state is lost) and rebuilds it. That's why you must never define components inside other components.
    • Keys identify children across renders. With stable keys, React can move, insert and remove list items. Using the array index as a key breaks when items are reordered or inserted, mixing up state and inputs.
    Myth to correct

    The VDOM is not "faster than the DOM". It's overhead that buys a declarative programming model with good-enough performance. Svelte and Solid skip it by compiling to direct DOM updates, and signals update only the exact nodes that changed.

    Interviewer follow-ups

    Why is setTimeout(fn, 0) not actually 0 ms?

    It only queues a task after at least 0 ms. The task waits until the stack is empty and all microtasks are drained, and possibly until a render finishes. Browsers clamp nested timers (depth ≥ 5) to a 4 ms minimum and throttle timers in background tabs to 1 s or more. For "run right after the current work", use queueMicrotask; for "yield to the browser", use scheduler.yield() or MessageChannel.

    How do you find and fix a memory leak in a SPA?

    Reproduce by navigating to and away from a view repeatedly. In DevTools Memory, take heap snapshots (baseline → after N cycles → after GC) and compare them, looking for detached DOM nodes and growing arrays or maps. Typical culprits: event listeners or intervals not removed in effect cleanups, subscriptions not unsubscribed, module-level caches without eviction, and closures holding large objects. Fix with cleanups, AbortController for listeners and fetches, and WeakMap/WeakRef for caches.

    What does the event loop look like inside a Web Worker?

    Each worker has its own thread, call stack, heap and event loop (tasks and microtasks), but no rendering steps and no DOM. Communication happens through postMessage, which uses the structured clone algorithm (a copy). Use transferable objects (ArrayBuffer, OffscreenCanvas) for zero-copy transfer, or SharedArrayBuffer + Atomics (which require cross-origin isolation) for shared memory.

    The browser turns HTML and CSS into pixels through DOM + CSSOM → style → layout → paint → composite.     The cascade and specificity

    4. Cascade layers (@layer): later layers win, and un-layered styles beat all layers.

    Accessibility engineering

    • Semantic HTML first: <button> gives you focus, Enter and Space activation, and the button role for free. A <div onClick> gives you none of that. Use landmarks (<header>, <nav>, <main>, <footer>) and a logical heading hierarchy.

    Interviewer follow-ups

    An animation is janky. How do you debug it?

    Record in the DevTools Performance panel with CPU throttling. Look for long tasks, purple Layout and green Paint blocks every frame, and "Forced reflow" warnings.     How do you build an accessible custom dropdown (combobox)?

    Follow the WAI-ARIA Authoring Practices combobox pattern: an input with role="combobox", aria-expanded, aria-controls pointing at a role="listbox", and options with role="option" and aria-selected.     What's the difference between display:none, visibility:hidden and opacity:0?

    display: none removes the element from layout and the accessibility tree. visibility: hidden keeps its space, but it isn't visible, focusable or announced. opacity: 0 keeps space, stays focusable and clickable, and is still announced (a common accessibility trap).     HTTP vs HTTPS and the TLS handshake

    HTTPS = HTTP over TLS. It provides confidentiality (encryption), integrity (tamper detection) and authentication (the server proves identity with a CA-signed certificate). It's also required for HTTP/2 in browsers, Service Workers, geolocation, and most modern APIs.

    1
    TCP 3-way handshake: SYN → SYN-ACK → ACK (1 RTT). HTTP/3 skips this by using QUIC over UDP.
    2
    ClientHello: supported TLS versions and cipher suites, a random value, SNI (the hostname), ALPN (h2 or http/1.1), and the client's key share (ephemeral ECDHE public key).
    3
    ServerHello + key share: both sides now derive the shared secret (ECDHE) and handshake keys. The server then sends its encrypted Certificate, a CertificateVerify signature proving it owns the private key, and Finished.
    4
    Client verifies the certificate chain up to a trusted root CA, the hostname, expiry and revocation, then sends Finished. TLS 1.3 completes in 1 RTT (TLS 1.2 needed 2), and resumed sessions can use 0-RTT.
    5
    Application data is encrypted with fast symmetric ciphers (AES-GCM, ChaCha20-Poly1305) using session keys. Ephemeral keys give forward secrecy: a leaked server key can't decrypt past traffic.

    Polyfills: the Custom Promise example

    A polyfill implements a standard API in environments that lack it, usually feature-detected first (if (!window.Promise) { … }). The simple version below is a classic warm-up:

    function CustomPromise(executor) {
  let onResolve, value, isFulfilled = false;
  function resolve(val) {
    value = val; isFulfilled = true;
    if (typeof onResolve === 'function') onResolve(val);
  }
  this.then = function(callback) {
    onResolve = callback;
    if (isFulfilled) callback(value);
    return this;
  };
  executor(resolve);
}
    What a staff-level interviewer expects you to point out
    • No rejection path, and executor exceptions aren't caught.
    • then returns this instead of a new promise, so chaining doesn't transform values.
    • Only one callback is stored; multiple .then calls overwrite each other.
    • Callbacks run synchronously; the spec requires microtask scheduling.
    • It can resolve multiple times, and it doesn't adopt the state of returned promises or thenables.

    class MyPromise {
  #state = 'pending';
  #value;
  #handlers = [];

  constructor(executor) {
    let called = false;
    const once = (fn) => (arg) => { if (!called) { called = true; fn(arg); } };
    const resolve = once((v) => this.#resolve(v));
    const reject = once((e) => this.#settle('rejected', e));
    try { executor(resolve, reject); } catch (e) { reject(e); }
  }

  #resolve(value) {
    if (value === this) return this.#settle('rejected', new TypeError('Chaining cycle'));
    if (value !== null && (typeof value === 'object' || typeof value === 'function')) {
      let then;
      try { then = value.then; } catch (e) { return this.#settle('rejected', e); }
      if (typeof then === 'function') {              // adopt thenable state
        let done = false;
        try {
          then.call(value,
            (v) => { if (!done) { done = true; this.#resolve(v); } },
            (e) => { if (!done) { done = true; this.#settle('rejected', e); } });
        } catch (e) { if (!done) { done = true; this.#settle('rejected', e); } }
        return;
      }
    }
    this.#settle('fulfilled', value);
  }

  #settle(state, value) {
    if (this.#state !== 'pending') return;
    this.#state = state;
    this.#value = value;
    this.#handlers.forEach((h) => h());
    this.#handlers = [];
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      const run = () => queueMicrotask(() => {         // async, per spec
        const fulfilled = this.#state === 'fulfilled';
        const handler = fulfilled ? onFulfilled : onRejected;
        if (typeof handler !== 'function') {            // pass-through
          return fulfilled ? resolve(this.#value) : reject(this.#value);
        }
        try { resolve(handler(this.#value)); } catch (e) { reject(e); }
      });
      this.#state === 'pending' ? this.#handlers.push(run) : run();
    });
  }

  catch(onRejected) { return this.then(undefined, onRejected); }

  finally(fn) {
    return this.then(
      (v) => MyPromise.resolve(fn()).then(() => v),
      (e) => MyPromise.resolve(fn()).then(() => { throw e; }));
  }

  static resolve(v) { return v instanceof MyPromise ? v : new MyPromise((r) => r(v)); }
  static reject(e) { return new MyPromise((_, r) => r(e)); }

  static all(iterable) {
    return new MyPromise((resolve, reject) => {
      const items = [...iterable];
      const results = new Array(items.length);
      let remaining = items.length;
      if (remaining === 0) return resolve(results);
      items.forEach((item, i) => {
        MyPromise.resolve(item).then((v) => {
          results[i] = v;                                 // preserve order
          if (--remaining === 0) resolve(results);
        }, reject);                                       // fail fast
      });
    });
  }
}

    function debounce(fn, ms) {
  let t;
  return function (...args) {
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), ms);
  };
}

function throttle(fn, ms) {
  let last = 0, timer;
  return function (...args) {
    const now = Date.now();
    const remaining = ms - (now - last);
    if (remaining <= 0) {
      clearTimeout(timer); timer = null;
      last = now; fn.apply(this, args);
    } else if (!timer) {                                // trailing call
      timer = setTimeout(() => { last = Date.now(); timer = null; fn.apply(this, args); }, remaining);
    }
  };
}
