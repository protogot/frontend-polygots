Rendering Strategies Deep Dive
CSR vs SSR vs SSG vs ISR

Executive Summary & Core Definitions

Rendering strategies determine where and when HTML markup and JavaScript code execution occur relative to a client request. The choice directly affects Core Web Vitals (TTFB, FCP, LCP, CLS), infrastructure costs, and search engine indexability.

CSR

Server sends a bare HTML shell. Browser downloads, parses, and executes JS which constructs the DOM and fetches API data dynamically.

SSR

Server dynamically generates complete HTML on every request by executing server-side JS and resolving data fetches before responding.

SSG

HTML pages are pre-rendered entirely at build time. Static files are deployed directly to a CDN edge node.

ISR

Extension of SSG that regenerates or updates static pages in the background on-demand or per revalidation interval.

Architectural Comparison Matrix

Strategy Execution Environment TTFB Ideal Use Case
CSR Browser Fast (static shell) Authenticated dashboards, SaaS apps, internal tools
SSR Node.js / Edge Server Slower (DB/API bound) Dynamic e-commerce, news feeds, personalized portals
SSG Build Engine / CI/CD Ultra-Fast (CDN edge) Blogs, docs, marketing landing pages
ISR CDN Edge + Node Engine Ultra-Fast (stale cache) Product catalogs (10k+ pages), dynamic blogs

In-Depth Breakdown & Technical Mechanics

1. Client-Side Rendering (CSR)

Client requests URL → Server returns <div id="app"> + JS bundle
Browser parses JS → Client makes API calls → React/Vue updates DOM

Performance: High TTI and LCP latency on low-end devices due to network waterfalling (HTML → JS → API → Render). Zero server compute per request. Hydration: N/A.

2. Server-Side Rendering (SSR)

Server executes component logic & data fetching → streams/sends HTML string
Client renders HTML instantly → downloads JS → browser hydrates DOM
Hydration Pitfall — “Uncanny Valley”

Users see complete UI quickly (fast FCP), but click events do not respond until hydration JS finishes attaching listeners.

Bottlenecks: High server CPU; TTFB bound by slowest upstream API unless using Streaming SSR (React 18 Suspense).

3. Static Site Generation (SSG)

Build pipeline runs getStaticProps → compiles all routes into HTML + JSON → assets pushed to S3/CDN. Near 0ms TTFB globally; highly resilient to traffic spikes.

Trade-off: Build times scale linearly with page count (O(N)). Unsuitable for highly dynamic sub-second data.

4. Incremental Static Regeneration (ISR)

  1. User requests /products/123 — CDN serves cached static HTML
  2. If revalidate time (e.g. 60s) has passed, serve stale content while triggering background regeneration
  3. Once regenerated, CDN edge cache updates globally
  4. On-Demand Invalidation: Event-driven cache purging via webhooks (CMS update → tag invalidation)

Interviewer Follow-Ups

How does Streaming SSR with HTML Shell differ from traditional SSR?
Traditional SSR blocks the entire document until all data requests finish (renderToString). Streaming SSR (renderToReadableStream / React 18 Suspense) sends an initial HTML shell immediately, streaming chunks as backend promises resolve — reducing TTFB and enabling Selective Hydration.
What is the “Hydration Mismatch” error and how do you resolve it?
Occurs when server DOM ≠ client initial render (e.g. window.innerWidth, dynamic IDs, timestamps). Browser discards server nodes and re-renders from scratch. Fix: deferred client-side rendering via layout effects, or ensure deterministic data access.

Web Performance & CDN Architecture

Techniques to Optimize Page Landing Speed

  • Critical Rendering Path: Inline critical CSS, defer non-critical JS via defer/async, preconnect to third-party domains (<link rel="preconnect">)
  • Resource Prioritization: Route-based code splitting, dynamic import(), adaptive preloading (<link rel="preload">), AVIF/WebP with srcset
  • Caching & Edge: Serve static assets via Edge CDNs, immutable caching (Cache-Control: public, max-age=31536000, immutable), HTTP/2 multiplexing, HTTP/3 QUIC, Brotli

CDN Internal Mechanics & Cache Invalidation

How a CDN works: Anycast DNS routes clients to the nearest PoP edge node. On cache miss, the edge proxies to origin, caches the response per headers, and serves subsequent hits from memory/SSD.

What to cache at the edge: Content-hashed JS/CSS bundles, media, static HTML, public REST/GraphQL endpoints, web fonts.

Invalidation mechanisms:

  • Cache Busting — content-addressed filenames (main.a1b2c3.js)
  • Programmatic Purging — API-driven URL/Tag invalidation
  • Revalidation — stale-while-revalidate or conditional ETag / If-None-Match

Client-Side Storage, Auth Tokens & Security
XSS vs CSRF

Storage Mechanisms & Token Architecture

MechanismCharacteristics
localStoragePersistent key-value, synchronous
sessionStorageTab-scoped key-value
CookiesSent with HTTP requests; supports Secure attributes
IndexedDBAsync transactional NoSQL for large structured / offline data
Token Storage Best Practice

Store tokens in HttpOnly, Secure, SameSite=Strict/Lax cookies. Access tokens in JS memory + HttpOnly refresh cookies = optimal balance.

Security Trade-offs

localStorage is fully vulnerable to XSS (any injected script can read tokens). Cookies mitigate XSS exfiltration via HttpOnly but introduce CSRF if not guarded by SameSite or CSRF tokens.

XSS and CSRF Deep Dive

Cross-Site Scripting (XSS)

Malicious JS executes in the user’s browser (Stored, Reflected, or DOM-based).

Mitigations: Context-aware output encoding, CSP headers, avoid dangerouslySetInnerHTML, sanitize with DOMPurify.

Cross-Site Request Forgery (CSRF)

A malicious site tricks the browser into executing an unwanted action on a trusted authenticated site.

Mitigations: SameSite=Strict/Lax cookies, anti-CSRF tokens (Synchronizer Token Pattern), custom Authorization headers (Bearer), CORS policy.

React State Architecture & URL-Driven Filters

State Management Solutions

  • Local State (useState / useReducer) — High encapsulation, zero boilerplate; limited to localized UI; prop-drilling risk
  • Context API — Built-in DI for static/low-frequency global state (theme, locale); re-renders all consumers on any change
  • Global Store (Redux Toolkit / Zustand / Recoil) — Centralized predictable tree, unidirectional flow, selector subscriptions
  • Server State (React Query / RTK Query) — Decouples fetching, polling, caching, optimistic updates from UI logic

Managing Search & Filter State

URL Search Parameters = Gold Standard

Query strings for complex catalog/search filtering enable deep linking, back/forward history, and shareable URLs. Prefer over global store unless filters must persist across unmounted layouts without polluting public URLs.

Funnel Analytics Pipeline

Event schema: search_executed → item_viewed → booking_initiated → payment_completed

Implementation: Use navigator.sendBeacon() or background workers to transmit without blocking unload. Attach unified context (sessionId, userId, correlationId, timestamp, device metadata).

Frontend Testing Strategies & Flaky Dependencies

Testing Pyramid

  • Unit (Vitest/Jest) — Pure functions, hooks, utilities; near-instant feedback
  • Integration (React Testing Library) — User-perspective DOM interactions via accessible roles; no implementation mocking
  • E2E (Playwright/Cypress) — Multi-step critical journeys across real browsers

Isolating External Dependencies

  • MSW (Mock Service Worker) — Intercepts HTTP/GraphQL at the Service Worker level; keeps app code identical in dev and test
  • Module Spies (vi.mock() / jest.mock()) — Replace third-party SDKs (analytics, payments) for deterministic suites

08

JavaScript Runtime Internals
Event Loop & Virtual DOM

Event Loop & Task Queue Lifecycle

  • Call Stack — Single-threaded execution tracking active frames
  • Microtask Queue — Promises, queueMicrotask(), MutationObserver. Drained entirely before yielding
  • Macrotask Queue — setTimeout, setInterval, I/O, user input. One task per loop iteration
  • Render Steps — Style calc, layout, paint (synced with requestAnimationFrame) before next macrotask

V8 Engine Pipeline & Virtual DOM

V8: Source → Parser → AST → Ignition Interpreter (bytecode) → TurboFan JIT (hot paths → machine code, with de-opt fallbacks)

Virtual DOM: In-memory JSON of the real DOM. On state change, React builds a new tree, runs Diffing (O(N) heuristic via stable keys + element type), batches real DOM mutations.

Advanced CSS, Accessibility & DOM Painting

Core CSS Concepts & Layout

  • Specificity: 3-tuple (Inline, IDs, Classes/Attrs/Pseudo-classes, Elements/Pseudo-elements)
  • Box Model: content-box adds border/padding outside; border-box includes them in width
  • Grid vs Flexbox: Grid = 2D layout; Flexbox = 1D directional alignment
  • Animations: Target GPU properties (transform, opacity) to skip Layout & Paint

Browser Rendering Pipeline & a11y

HTML → DOM + CSS → CSSOM
Render Tree Construction
Layout (Reflow) → Paint (Rasterization) → Composite (GPU layers)

Accessibility: Semantic HTML (<main>, <nav>, <button>), focus traps for dialogs, ARIA live regions (aria-live="polite"), visible keyboard focus.

Micro-Frontends, Virtualization & Bundlers

Micro-Frontends vs Monoliths

Decompose into independently deployable feature apps managed by separate teams. Integration models: build-time (npm), server-side edge routing, iFrames, Webpack Module Federation (runtime).

Module Federation: Dynamically load remote code bundles at runtime without shared build-time compilation or duplicating shared deps (e.g. React).

List Virtualization & Tooling

  • react-window / react-virtualized — Render only viewport-visible items for massive lists (100k+ rows); reuse nodes on scroll
  • Babel — Transpiles ESNext/JSX to backward-compatible JS via targets + polyfills (core-js)

Generators: Functions that yield control, returning iterators { value, done }.

Custom Promise Polyfill:

function CustomPromise(executor) {
  let onResolve, value, isFulfilled = false;
  function resolve(val) {
    value = val; isFulfilled = true;
    if (typeof onResolve === 'function') onResolve(val);
  }
  this.then = function(callback) {
    onResolve = callback;
    if (isFulfilled) callback(value);
    return this;
  };
  executor(resolve);
}
